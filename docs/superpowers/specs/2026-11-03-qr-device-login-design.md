# Flixify phone-approved device login

Approved intent: the user explicitly asked to implement, test and publish the researched QR login on Android TV, web, macOS and Windows. Keep manual16-character account-code login, registration,3h trials, welcome offers, packages and stream concurrency unchanged. This is first-party device linking inspired by RFC8628, not a claim of OAuth conformance. No passkey/Bluetooth implementation is included.

## User journey
Target login displays a QR, eight-character code, countdown, renewal and existing manual login. Phone camera opens proposed `https://flixify.vip/cihaz?code=BCDF-GHJK`. A logged-out phone signs in through existing login then returns to this exact pending page; no arbitrary return URL. A signed-in phone sees its account suffix, device label/platform and matching code, and explicitly approves or denies. GET/preview never approves. The target receives its own normal session and continues existing welcome/access flow. Expired packages still reach renewal; pairing creates no account/trial/provider line. Add phone Hesabım → Cihaz bağla short-code entry for PWA/browser storage separation. Preserve all current style and colors; QR is sharp black/white with a four-module quiet zone.

## Binding public API v1 (all new POST routes)
All replies no-store, no-referrer; no raw secret logging or analytics. Production phone lookup/decision requires first-party Origin plus current Bearer auth. Origin is defense in depth, not authentication; native start/token/ack/cancel use their own private secret. Existing CORS is not sufficient approval authorization.

- `/auth/device/start` input `{platform: "android_tv"|"web"|"macos"|"windows", deviceName:string, installationId?:string}`. Response `{requestId:UUID, deviceSecret:base64url, userCode:string, verificationUri:"https://flixify.vip/cihaz", verificationUriComplete:string, qrPngBase64:string, expiresAt:ISO8601, expiresInSeconds:180, intervalSeconds:2}`. Display code format XXXX-XXXX using nonambiguous letters. Device secret is32 cryptographically random bytes, stays only in target memory; only its verifier is stored. QR PNG is generated by the first-party API from the public verification URL, never an external image service. Clients validate image byte and dimension bounds; no camera permission or QR library on native clients.
- `/auth/device/token` input `{requestId,deviceSecret}`. Reply `{status:"pending"|"authorized"|"slow_down"|"denied"|"cancelled"|"expired"|"complete", intervalSeconds?:number, session?:{accessToken,refreshToken,user:{id,codeSuffix}}}`. Only authorized carries session. Honor server interval; one poll at a time, backoff on network/429/slow_down. Terminal states stop. Do not automatically create a new challenge on expiry.
- `/auth/device/ack` input `{requestId,deviceSecret}`. Reply `{status:"complete"}` after successful local token adoption. Repeat is idempotent. A first authenticated use of the issued session also activates/acknowledges delivery, avoiding loss of a working login after a lost ACK.
- `/auth/device/cancel` input `{requestId,deviceSecret}`. Reply `{status:"cancelled"|"complete"}`. Before completed, cancel wins a transaction and revokes any issued session family, including its rotated descendants. After completed, the normal device-management revocation flow applies.
- `/auth/device/lookup` phone Bearer input `{code:string}`. Reply `{requestId,userCode,deviceName,platform,expiresAt,approvalNonce,accountSuffix,state}`. Requires an active account-code-authenticated session. A device-linked phone session receives403 `{reason:"reauthentication_required",message}` and can use preserved manual login to authorize further devices. Nonce is bound to account and request, not the rotating approver SID.
- `/auth/device/decision` phone Bearer input `{requestId,userCode,approvalNonce,action:"approve"|"deny"}`. Reply `{status:"approved"|"denied"|"complete"}`. Approval permanently binds one account; no overwrite by another account. Approver SID is audit context; normal phone refresh/local logout does not undo explicit short-lived approval. Explicit cancellation, account block/deletion and expiry remain authoritative.
- Malformed input400, unavailable/missing state404, repeated/other-account decision409, rate limit429, infrastructure failure503. Never include raw request/secret in user-visible errors. Custom reasons are not mislabeled as RFC OAuth errors.

## Server authority and delivery
PostgreSQL is the sole authority. Indexed challenge/rate tables, real DB time/expiry, row locks, uniqueness and transaction-aware session insertion enforce at most one issued target session per approval. Creation and lookup have shared rate limits, not process-local Map-only state. Polls do no scrypt, provider/catalog/trial work. Default initial poll2s; early polling slows down by5s. Proposed caps: start60/IP/min plus5 active per installation; lookup/decision30/IP/min and decision30/account/min; token/ack/cancel90/request/min. Limits are independent of account-registration quotas. Use keyed hashes for rate identifiers.

The public approval deadline is180s. An approval accepted before that deadline permits a separate60s delivery window. Approval precomputes the random refresh secret/hash and token pair outside the row lock after phone authentication/rate/nonce validation; the approval transaction issues exactly one target session family. The first issuance records exactly one target session family and a short-lived encrypted response envelope in the same transaction; retry by the same private target proof returns that same envelope, not another session. ACK/authenticated first use removes the envelope and completes the request. Unactivated undelivered issuance expires and is revoked; activated sessions survive lost ACK. Old envelopes and expired pending requests are removed opportunistically and by bounded cleanup. Key handling reuses established server secret primitives with purpose separation; no new public client secret.

Add session `auth_method` (default account_code) and stable `family_id`; preserve both across refresh. QR-issued sessions are device_link, and cannot export the reusable account code or authorize another device. Code-bearing viewer response projections must redact nested/top-level master code for these sessions; manual login/registration and existing full-code owner UX stay compatible. This is a narrow origin distinction, not a new streaming-only permissions model. Existing device listing/revocation continues, backed by stable session family for pending cancellation.

## Client lifecycle
Start only on the QR login surface. Pause/abort polls when hidden/backgrounded; invalidate old attempts on Cancel, manual login, logout, regeneration, expiry, replacement and process restart. Never persist an unfinished pairing secret. Check attempt identity/cancellation immediately before secure store/saveSession. A late authorized response must not sign in in the background; best-effort server cancellation cleans any unadopted issuance. After tokens are saved, retry account/welcome/provider bootstrap using that session; never mint another session because post-login data failed. ACK follows adoption and can retry; normal authenticated first use supplies recovery. Never replace a different current account due to a late poll.

Native token storage remains AndroidKeyStore/Keychain/DPAPI. Web retains current session-installation lifecycle; no claim that localStorage is equivalent to OS encrypted storage. Pairing routes are excluded from URL/event analytics; only sanitized operation/outcome/platform/duration events may be added deliberately. No master code, request/code, private proof, provider credential or token in QR, telemetry, logs, or external services. QR alone and code matching do not prove proximity or prevent a relayed legitimate QR; device labels are untrusted hints.

## Builder-check resolutions (binding)
- Target countdown reaching zero does not override server authority. Perform the bounded final status polls for at most the additional60s delivery grace; stop on server terminal status. Never replace an approved request merely because local countdown reached180s. Use response duration plus monotonic elapsed time, not trust in the device wall clock.
- Lookup `state` is pending|approved|issued|completed|denied|cancelled|expired; `approvalNonce` is present only for pending. Phone re-lookup after lost decision response displays already-approved/complete status and never submits a fresh request or changes account binding.
- Issue token material during approval (precompute scrypt before transaction), not in target polling. Polls only read/return an existing encrypted delivery envelope. An approval accepted at179s retains its60s delivery window.
- The challenge row remains as the durable family anchor while its device-linked sessions exist. `family_id` for linked sessions is the challenge UUID; normal preexisting/manual sessions may leave it null. Paired refresh, cancellation, activation/ACK, cleanup and linked-device revocation lock that same anchor and re-read session status before any insert. A refresh that waited behind cancellation cannot create an active descendant. Code-authenticated refresh keeps its existing behavior.
- Approval/paired refresh acquire the user's row (FOR SHARE) before the family/challenge row, and revalidate status. Explicit global block/delete revokes linked anchors before sessions. This prevents a not-yet-committed linked session escaping a block. Keep lock order consistent and test actual PostgreSQL races.
- Token adoption marks a local attempt adopted before notifying the UI. Hiding after successful adoption is not Cancel. ACK can retry; first authenticated use activates the same family. Undelivered/unactivated cleanup must not revoke a working session after a lost ACK. Pairing cancellation only revokes uncompleted delivery; completed sessions use existing device management.
